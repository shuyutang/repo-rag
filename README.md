# repo-rag

A retrieval-augmented engineering assistant for large Python repositories. It
indexes **source, tests, documentation and git history** into one knowledge
base, retrieves with **dense + BM25 + symbol + history** retrieval, fuses and
reranks the candidates, optionally runs **iterative agentic retrieval**, and
answers with **file/symbol/line-level citations** that are validated against the
retrieved evidence.

The point of the project is not that it answers questions — it is that every
component had to **earn its place on a benchmark**, including the two that did
not. See [docs/evaluation.md](docs/evaluation.md).

The demo repository is [vLLM](https://github.com/vllm-project/vllm): 60,272
chunks from 4,150 files plus 3,000 commits.

---

## Quick start

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -e .

./scripts/serve_llm.sh &                                  # Qwen3-4B on :8099, no API key
./scripts/index_repo.sh https://github.com/vllm-project/vllm
./scripts/index_repo.sh https://github.com/vllm-project/vllm --serve
```

`index_repo.sh` works on **any Python repository** and does setup and refresh
alike: it clones or pulls, then rebuilds the index only if the checkout moved.
Re-run it (or cron it) to stay current. `--serve` opens the UI on
<http://127.0.0.1:8100>.

```bash
.venv/bin/rag ask "Where is KV cache memory allocated and how is its capacity determined?" --trace
.venv/bin/rag search "allocate_slots"
.venv/bin/rag impact allocate_slots
```

Timings on one RTX 4090: ingest 15 s, index 53 s, warm retrieval 5–140 ms, full
answer 5–12 s. Full command reference, API and UI guide: [docs/usage.md](docs/usage.md).

## How it works

```
repository ─┬─ code parser (ast)      ─┐
            ├─ document parser        ─┤
            └─ git parser             ─┴─> chunks ─┬─> vector index (MiniLM)
                                                   ├─> BM25 index (code tokenizer)
                                                   ├─> symbol index (exact + fuzzy)
                                                   └─> symbol graph (callers/tests/imports)
                                                            │
   question ─> planner ─> retrievers ─> RRF fusion ─> reranker ─> [agent loop] ─>
               context builder (budget, dedup, quotas) ─> LLM ─> grounded answer
                                                            │
                                                          trace
```

Chunks are **symbols, not windows** — one per function, method, class overview
and module, carrying `path, symbol, qualified_name, symbol_type, start_line,
end_line, imports, references`. That provenance is what makes line-level
citations, symbol lookup and the change-impact graph possible.

Design rationale for every stage: [docs/architecture.md](docs/architecture.md).

## Results

| System | Recall@10 | MRR | Answer accuracy | Citation validity | Retrieval p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| dense | 0.506 | 0.413 | 0.867 | 0.898 | 5 ms |
| bm25 | 0.729 | 0.715 | 0.942 | 0.925 | 0 ms |
| hybrid | 0.713 | 0.723 | 0.942 | 0.833 | 52 ms |
| hybrid+rerank | 0.716 | 0.725 | 0.925 | 0.894 | 122 ms |
| **agentic** | **0.735** | **0.736** | 0.942 | **0.950** | 2246 ms |

113 questions, test split. Full table with every metric:
[docs/results_table.md](docs/results_table.md) — generated by `rag report`,
nothing hand-written.

In one paragraph: **BM25 with a code-aware tokenizer is the strongest single
retriever**, dense retrieval alone is far behind, RRF fusion buys ranking
quality rather than recall, the generic cross-encoder **reranker does not pay
for itself** on a single fused list (though it does when the agent merges
evidence from four tools), and **agentic retrieval wins on every metric** at 18×
the retrieval latency. Three of the PRD's five techniques earned their place;
the other two are reported as-is rather than quietly dropped.

The aggregate hides the interesting split: on the 19 hand-written multi-hop
questions in the test set, recall@10 falls to **~0.30 for every configuration**.
That gap, and what to do about it, is
[docs/failure_analysis.md](docs/failure_analysis.md).
